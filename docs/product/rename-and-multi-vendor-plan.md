# 产品计划：改名 dsh-connect-desktop + 多供应商演进

- 目标：把已上线的 `dsh-connect-loomy`（v0.1.2）演进为 `dsh-connect-desktop`，在同一包内接入第二家供应商「商汤小浣熊（Raccoon）」，并为第三家预留位置。
- 硬约束：① 不影响老用户的**会话**与**账号数据**；② 老用户迁移最多两个粘贴块；③ 改名后市场条目必须重新提交。
- 本文日期：2026-11-17。上游事实来源：`README.md`、[插件契约](../dsh-plugin-contract.md)、`package.json`、`cordis.patch.yml`、`src/shared/paths.ts`、`src/accounts.ts`、`.github/workflows/release.yml`。

---

## 0. 结论先行

1. **名字选 `desktop`，不选 `signin`。** 我们卖的不是"登录"，是"复用你已经付费的桌面端授权"。`desktop` 是稳定的接入类别，`signin` 是会过期的实现手段——名字里写手段，等于每换一家供应商就改一次名。
2. **改名发生在 0.2.0，与第二家供应商同版发布**；不打单独的"纯改名版"（用户不会为改个名字做迁移）。
3. **必须冻结的只有两类标识符**，其余全部可换：
   - 会话相关（**永久冻结**）：路由键 `loomy` / `loomy-2..n` / `loomy-pool`、模型 identity 的 `provider='loomy'`、`api='openai-completions'`。DSH 的历史消息带这三个字段，改一个就等于把历史当成"别的模型"。
   - 账号数据（**目录冻结、命名空间可继承**）：`$DSH_HOME/storages/dsh-connect-loomy/` 继续用；设置命名空间从 `dsh-connect-loomy` 切到 `dsh-connect-desktop`，启动时一次性继承旧用户层。
4. **两条命令成立的前提是先发 0.1.3「墓碑提醒版」**，但 **0.2.0 绝不允许依赖用户装过 0.1.3**（大多数人会直接跳版）。
5. 改名有个副作用要正面对待：旧名会留给市场上那份同名第三方实现。沟通里必须给**仓库全限定地址**，不能只说包名。

## 1. 现状盘点：哪些字符串被"用户数据"钉住了

| 标识符 | 现值 | 写入了哪里 | 改名的后果 | 处置 |
|---|---|---|---|---|
| 数据目录 | `$DSH_HOME/storages/dsh-connect-loomy/` | `accounts.json`（登录凭证 + 账号列表）、`auth-session.json`（插件自己登录的副本）、`state.json`（模型选择、随机池开关、当前账号） | 换目录 = 老用户看到"账号没了"，等同数据丢失 | **冻结**，代码里作为 `LEGACY_DATA_ID` 常量表达，与包名解耦 |
| 路由键 | `loomy`、`loomy-N`、`loomy-pool` | 模型选择器、`registerAdapter`、历史消息 | 改键 → `isSameModel` 不成立 → 历史 thinking 被丢（1.5.2）或降级成正文（旧版） | **永久冻结**；新供应商用 `raccoon` / `raccoon-pool`，不共用键 |
| 模型 identity | `provider: 'loomy'` | 每条 assistant 消息 | 同上，且 `requireProvider` 可能直接抛 `Unknown provider` | **永久冻结** |
| `api` 协议串 | `openai-completions` | 模型对象、`profile.api` | 与 identity 联合判定，写错即全量失配 | **永久冻结** |
| 设置命名空间 | `dsh-connect-loomy`（= loader 条目 id） | profile 的 patch YAML（`enabled`、`baseURL`、缓存等用户层） | 直接换 ns → 用户显式关掉插件的 `enabled:false`、自定义 baseURL 全部"复活"成默认值 | 0.2.0 切换 ns，**启动时一次性继承**：仅当新 ns 无用户层时，把旧 ns 用户层里的字段拷过去；旧 ns 原样保留不删 |
| HTTP 前缀 | `/plugins/dsh-connect-loomy` | 浏览器缓存里的旧 client bundle | 换前缀 + 浏览器缓存 = 旧 bundle 打到 404，卡片/胶囊空白 | 0.2.x **双前缀注册**（新旧都答），客户端用新前缀；0.3.0 撤旧 |
| client bundle id | `dsh-connect-loomy` | `window.__ModuleLoader__.load({id})`、require 表 | 不持久化，仅加载期键 | 0.2.0 换新 id，无迁移动作 |
| locale 命名空间 | `settings.loomy` | 仅 UI 文案键 | 不持久化 | 可保持，避免无谓改动 |
| bin 名 | `dsh-connect-loomy` | 用户/脚本里的 `node lib/bin.js status --json` | 破坏已有脚本 | 0.2.x 新名 + 旧名别名；0.3.0 起旧名仅告警 |
| 市场资产名 | `dsh-connect-loomy.tgz`（`releases/latest/download/…`，刻意不带版本号） | 市场条目下载链接 | 改名后旧链接若 404，老条目就装不上 | 新资产 `dsh-connect-desktop.tgz`；**旧资产继续发至少 3 个月** |

一句话：**配置可以搬，历史不能搬，凭证必须原地读。**

## 2. 产品定位与命名叙事

### 2.1 一句话定位

> 把本机**桌面客户端里已经登录/已付费**的模型，接进 DSH 的模型选择器；不提供账号、不共享凭据、不绕过计费，只读展示余额。

### 2.2 为什么是 `desktop`，不是 `signin`

| 维度 | `desktop` | `signin` |
|---|---|---|
| 描述的是 | 价值来源：桌面端已有的授权与额度 | 实现手段：一次登录动作 |
| 用户预期 | "我电脑上已经装了的那个东西，能在这里用" | "这插件能帮我注册/开通账号"（我们明确不做，且会把计费责任揽到自己身上） |
| 稳定性 | 跨供应商稳定：Loomy、Raccoon、第三家都是桌面端 | 每家登录方式不同（短信 / 扫码 / 账密），名字半年就过期 |
| 安全叙事 | 数据留在桌面端，插件只读；卸载即断开 | 暗示凭据流经插件，需要额外解释才澄清 |
| 可搜索性 | 与市场那份同名第三方实现区隔，占据未被占用的名字 | 与"登录"泛词竞争，搜不到 |

命名规范（一次定死，后续不再讨论）：

- 包名 / 仓库名 / 市场条目 id：`dsh-connect-desktop`
- 显示名：`DSH Connect Desktop`，副标题「把桌面端已登录的模型接进 DSH」
- 供应商名（模型选择器里的分组）：`Loomy`、`商汤小浣熊（Raccoon）`——**供应商是实例，不是包**
- 拒绝：`dsh-connect-clients`（暗示客户端管理）、`dsh-connect-local`（与 localhost 混淆）、`dsh-connect-bridge`（技术词，无用户价值）、`dsh-connect-signin`、以及任何把供应商名写进包名的方案

### 2.3 与市场上同名实现的处置

改名不是"顺手"，是**必须**：同名两份实现，用户搜索时无法判断装的是谁的。改名后：

- 我们的名字独占 `dsh-connect-desktop`；旧名 `dsh-connect-loomy` 在市场上会留给对方。
- 所有对外文案给**全限定仓库地址**，不给裸包名。
- 0.1.3 与旧市场条目里写明：「旧名条目可能指向其它实现，请以 `github.com/diudiu62/dsh-connect-desktop` 为准」。

## 4. 迁移设计（两条命令怎么成立）

### 4.1 用户看到的迁移路径

**A. 市场用户（推荐）**

1. 卸载旧版：`dsh plugin --profile web remove dsh-connect-loomy`
2. 在市场里点安装 `DSH Connect Desktop`（或粘贴安装块）

**B. 克隆 + `link:` 用户（当前 README 的主路径）**

1. `dsh plugin --profile web remove dsh-connect-loomy`
2. 克隆 + 构建 + 挂载合成**一个**粘贴块（目录名用 `dsh-connect-desktop`）

两条命令的口径 = **两个粘贴块**；市场安装的第二次是点击。顺序必须写死：**先 remove，再动目录**——先改目录名会让 `link:` 指向不存在的路径，DSH 启动即报错。

### 4.2 为什么老用户不需要"迁移数据"

因为**数据目录名不跟着包名走**。0.2.0 继续读 `storages/dsh-connect-loomy/`，`accounts.json` 与 `auth-session.json` 原地不动，用户重装后直接看到原来的账号、原来的当前账号、原来的池开关。这就是"最多两条命令"能成立的全部原因；任何"复制/导出/再导入"的方案都不合格。

设置是唯一需要主动继承的东西（命名空间换了），由启动时的一次性继承兜住：新 ns 无用户层 → 拷旧 ns 用户层字段；新 ns 已有值 → 一律以新 ns 为准；旧 ns 行保留不删（用户自己看得见、删得掉）。

### 4.3 升级 / 降级矩阵（每格都要有测试）

| 从 ↓ 到 → | 0.1.2 | 0.1.3 | 0.2.0 |
|---|---|---|---|
| 0.1.2 | — | 数据一致、无提示 | 数据一致、设置继承、会话可续 |
| 0.1.3 | 可降级，账号不丢 | — | 同左 + 旧提示消失 |
| 0.2.0 | **可降级**：卸新装旧账号仍在（schema 只增不改） | 可降级 | — |
| 两家同时装 | 禁止：守卫拦下并给出移除命令 | 同左 | 同左 |

### 5.3 0.1.3 Release 正文骨架（可直接用）

| AC-11 | 降级 | 卸新装旧，账号仍在、无"数据损坏"提示 | 完整走一遍 |
| AC-12 | 诊断不泄密 | "复制诊断"里没有 session、手机号全码、用户 id | 人眼过一遍导出文本 |
| AC-13 | 市场可信度 | 新条目可搜到、版本号与 Release 一致、下载可用；旧条目带指向说明 | 市场实搜 + 下载校验 |

## 7. 失败场景与对策

| # | 失败场景 | 用户看到什么 | 触发条件 | 设计对策 | 验收 |
|---|---|---|---|---|---|
| F1 | 双装冲突 | 启动报 `an adapter for provider "loomy" is already registered`，像是宿主坏了 | 用户先装新再卸旧，或市场自动装了新版 | 守卫先于注册：检测同 profile 旧包 → 抛带插件名与人话的错误 + 移除命令 | AC-6 |
| F2 | 账号"消失" | 账号列表空，面板显示未登录 | 新包用了新数据目录 | 目录常量冻结；启动时**先读旧目录**，绝不先创建新空目录 | AC-1 |
| F3 | 设置被重置 | 用户之前关掉的插件又开了；自定义 baseURL 没了 | 换 ns 未继承 | 一次性继承：新 ns 空才拷，已有值不覆盖 | AC-4 |
| F4 | 会话"降级" | 历史里的思考过程不见了/变成正文 | 路由键或 identity 被改 | 三个字段永久冻结；新供应商另开键 | AC-2 |
| F5 | 卡片/胶囊空白 | 设置页有入口但内容空 | 浏览器缓存旧 client bundle + 新前缀 | 0.2.x 双前缀注册；响应 `no-store` | AC-10 |
| F6 | 降级即丢数据 | 降回 0.1.3 后账号列表空/报损坏 | 0.2.0 升了 schema 版本或改字段语义 | schema 只增不改；降级测试进 G2 门 | AC-11 |
| F7 | 装成别人家的 | 功能完全不对，甚至要求填 key | 用户搜旧名装到第三方同名实现 | 文案给全限定仓库地址；旧条目加指向说明；0.1.3 卡片写明 | AC-13 |
| F8 | 目录先改名再卸载 | DSH 启动即报插件加载失败 | 用户先 `mv` 目录再 remove | Release 正文写死顺序；错误信息里给出"先 remove"的指引 | AC-7 |
| F9 | 脚本失效 | 用户自己的脚本 `dsh-connect-loomy status` 报 command not found | bin 名切换 | 0.2.x 保留旧 bin 别名，输出弃用提示 | 手工跑一次 |
| F10 | 旧资产 404 | 旧市场条目点击安装失败 | 改名后删掉旧 Release 资产 | 旧资产名继续发布 ≥ 3 个月 | 下载校验 |
| F11 | 第二家拖垮第一家 | Loomy 也不能用了 | Raccoon 适配器初始化抛错冒泡到 `apply` | 每供应商独立 try/catch + 状态位；一家坏不影响另一家 | AC-8 |
| F12 | 静默失败 | 什么都没发生，也没有报错 | 无遥测，用户不反馈 | 设置卡片常驻"最后检测时间 + 失败原因 + 复制诊断" | AC-12 |

## 8. 明确不做

- 不做账号/凭据的云端同步或中转——定位是"本机桌面端授权复用"，越界即失去信任。
- 不做自动迁移守护进程、不做后台常驻升级器。
- 不发布 npm 包（市场按 GitHub 收录），因此也**不保留旧包名的 npm 别名**——维护两套发布链路换不来任何用户价值。
- 不为每家供应商开独立包（`dsh-connect-raccoon` 之类）：那会把"多供应商"变成"多插件打架"，回到 F1。
- 不做跨供应商余额合并展示：两种额度不是同一货币，合并即误导。
- 不在 0.2.0 里顺手做 UI 大改：改名期只能有一个变量在动。

## 10. 待验证假设（不要当事实用）

1. **没有遥测**：所有"迁移率"只能用 Release 资产下载量、Issue/群提问量做代理指标，别把它写成精确百分比目标。
2. **Raccoon 的本地登录态与额度接口**尚未验证，G3 之前一律按"未知"处理；若它没有桌面端本地凭据，`desktop` 叙事对第二家不成立，需回到命名讨论（这是本计划最大的单点风险）。
3. **市场上那份同名实现的活跃度未知**：若它比我们更容易被搜到，改名收益会打折，需要额外在 README/群里做"认准地址"的教育。
4. **两条命令是否真的够**取决于用户当前的安装方式分布（市场 vs 克隆），当前无数据；G1 期间用群投票补一个粗分布。
